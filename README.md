# GetAudio

从 B 站 / 抖音分享链接提取音频。Android 手机可直接解析公开链接、下载音轨、保存、播放与导出，不需要 GetAudio 服务器。

**当前版本 0.9.11**（versionCode 39）：手机直接提取公开链接（支持一次粘贴多条批量提取）、可选服务器提取与同步、分类及相似曲目候选；手机号＋密码账号、音频提取 Agent、14 张内置静态壁纸 + 3 张动图 + 3 段视频背景（全部静音，可自选图片/视频/动图，并可旋转、缩放、拖动选框决定露哪一块）、导入本地音频、库页拖动与字段排序、剪辑页试听。Agent 与账号功能需要连接服务器。

使用步骤、接口协议、记忆设计和验收状态见 [音频 Agent 与手机号账号说明](docs/agent-and-accounts.md)。

可选服务端是可信内网单机版本：分类依据标题与描述，不是音频听辨；跨平台相似结果仅供核对，不自动合并。平台联网能力受风控影响，具体实测见文末。

## 快速开始

### 服务端

```bash
sudo apt-get install -y ffmpeg
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt

# 提取一条
.venv/bin/python -m getaudio.cli extract "【标题-哔哩哔哩】 https://www.bilibili.com/video/BVxxxxxxxxxx/"

# 扫码登录（终端直接显示二维码）
.venv/bin/python -m getaudio.cli login --user me --platform bilibili

# 起服务
.venv/bin/uvicorn getaudio.api:app --host 127.0.0.1 --port 8800
```

分享文案整段粘进去就行，不用自己抠链接。

B 站合集链接可带 `?p=N` 提取指定分 P；各分 P 独立入库和去重。省略 `p` 或使用 `p=1` 都对应第一 P。

### Android

```bash
cd android
export JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64 ANDROID_HOME=/opt/android-sdk
./gradlew assembleDebug        # 产物在 app/build/outputs/apk/debug/
```

提取页直接展示分享文本输入框，提供粘贴、清空和提取操作。音频行的播放/暂停按钮位于右侧，并与当前播放状态同步。播放栏右侧以图标与文字显示当前播放方式，可直接点击切换；提供顺序播放、列表循环、单曲循环和随机播放。重命名时默认全选原名称，修改后同步更新当前播放列表及系统媒体信息，保留播放进度。睡眠定时可选择“播完整个音频再停”。默认播放列表持久化为实际列表，当前队列与保存内容同步；加入列表按音频 ID、平台作品编号和已有 SHA-256 去重。加入时间单独保存并显示到秒，日期筛选通过日历和时钟选择年月日时分。类别页只展示用户类别；返回按钮与类别路径分开展示。定时剩余时间在音频库的云端同步右侧和操作菜单显示，并提供取消入口。新建播放列表未填写名称时自动采用“列表1、列表2”等名称；添加音频时显示目标列表名称，播放列表弹窗显示当前列表名称、音频数量和“当前播放”标记，并支持改名及删除列表。

如果手机已有 APK 的签名与本机不同，可构建并行验证版，包名为 `com.getaudio.app.preview`，显示为“GetAudio”，不会覆盖原应用：

```bash
cd android
./gradlew assembleDebug -PgetaudioPreview=true
```

安装后在抖音或 B 站分享作品到 GetAudio，或在「提取」页粘贴链接。手机直接向原平台请求公开作品信息和音频，音频保存在 App 私有目录，可在「音频库」播放或点导出按钮选择手机文件位置。默认服务器地址为 `https://43.142.37.199/`，手机通过 Wi-Fi 或移动网络直接访问 tx，无需 Mac 或 USB。点击「从服务器提取」可由 tx 下载视频、提取音频并自动下载到手机。生产接口使用设备私有访问凭据，凭据不打包进 APK。手机端本地提取不需要 Ollama 或 API Key，也不进行 AI 分类。

公网 HTTPS 与证书自动续期已部署，详见 [tx 直连部署记录](deploy/tx-https/README.md)。`./scripts/connect-tx-phone.sh` 仅保留为开发调试工具，正式连接不使用它。

提取页会显示手机直提取的分步诊断，并可一键复制。遇到 403 时，诊断会区分短链、分享页、访客凭证、作品详情、浏览器重试和媒体下载；复制内容只含步骤、状态码和大小，不含 Cookie、API Key 或完整媒体地址。

抖音优先重复请求公开分享页，让手机自动取得访客 Cookie，并解析页面服务端提供的作品数据。若分享页没有作品数据，才尝试作品详情接口和浏览器重试。提取页始终显示「从服务器提取」入口，服务器地址在「我的 → 服务器设置」管理；只有主动点击时才会将分享文本发往设置中的 GetAudio 服务器，并把服务器处理好的音频下载到手机。服务器设置提供默认地址恢复和只读连接测试。提取成功后保留分享文本，方便用另一种方式重试。

### 博主批量与 v2 接口（后端先行）

服务端新增一组账号隔离的 `/v2/...` 接口：只给抖音号（或主页 URL）就能按范围批量下载该博主的作品音频，图文/图集配乐也会收；同时补齐 `/v2/resolve`、曲目读写/逻辑删除/恢复、提取任务、维护和定时抓取。完整 curl 示例见 [HTTP API 说明](docs/http-api.md)。

- 输入字段 `url` / `input` / `text` 任选其一；裸数字必须带 `platform=douyin|bilibili`，否则 400。
- 抖音号先走公开的 `iesdouyin user/info` 换 `sec_uid`，失败才回退浏览器搜索（要登录 Cookie）。
- 抖音主页用 Playwright 捕获页面自己签名的 `aweme/post` 响应；窗口按 `create_time` 倒序，置顶作品不会打乱范围。
- 下载复用 `pipeline.extract()` + `DouyinExtractor`；列表里已带播放地址时不再请求 `aweme/detail`。
- 任务单线程顺序执行，进程重启把 `running` 恢复为 `pending`；单条失败不影响整批，授权失效整批标 `failed` 可重试。

这些路由目前不在 Android DTO 中，作为**后端先行接口**在 `tests/test_api_contract.py` 里显式跳过。

**实测（2026-10-30，临时数据库 + 临时音频目录）**：抖音号 `67194609689` 经公开 `user/info` 换成 `sec_uid`（不需要登录）；Playwright 抓到主页 259 条作品，最新一条 `7699794704686239011`（2026-10-23，17.1s）按预取 aweme 下载为 MP3，415,059 字节，`ffprobe` 实测 17.16s、含 mp3 音频流；验证后临时库和音频已删除。该次没有使用登录 Cookie，属于匿名出口可用的情况；换 IP/账号仍可能遇到验证码（见 `docs/http-api.md`）。

## 几个不显然的设计决定

### 无损优先：能拷贝就绝不重编码

源音频本来就是有损压缩过的，再转一次 AAC 是第二次有损。所以先探测源编码，再选能直接容纳它的容器（aac→m4a、mp3→mp3、opus→ogg、flac→flac），拷出来的流和源**逐字节一致**。只有拷贝走不通才退回重编码。

实测：某条抖音视频源是 HE-AACv2 64kbps，早期的 192k 重编码版本 5.73 MB，无损拷贝版本 1.89 MB —— 重编码在把文件撑大的同时还损失了音质。

### 两个平台都没用 yt-dlp

- **B 站**：yt-dlp 要先抓视频 HTML 页，而该页在机房 IP 上被风控直接回 `412`。改走开放 API（`view` + WBI 签名的 `playurl`）就通了，还能只下 DASH 音频轨，省九成带宽。
- **抖音**：作品不可见时 yt-dlp 一律报 `Fresh cookies are needed`，掩盖了真实原因。原生实现读 `filter_reason` 翻成人话。

`ytdlp.py` 保留作备选，平台改接口时可临时顶一下。

### 抖音选路：完整性优先于干净

抖音一条视频有两路音频 —— `music.play_url`（原声 BGM，干净）和视频合成流音轨（含人声环境音）。做 BGM 库当然想要前者，但**原声条目常常只是 20 秒左右的片段**。

所以先比时长再下载：原声覆盖不到视频时长的 90% 就判定为片段，改走视频音轨。另外成品时长一律用 `ffprobe` 实测，不信接口字段 —— 接口的 `duration` 描述的是视频，不等于实际取到的音轨。

### 凭证：加密 + AAD 绑定

登录 cookie 等同于账号本身，AES-GCM 加密后存库，正式环境的密钥从环境变量读；未设置时本地开发密钥保存在 `data/.secret_key`（权限 600，已忽略入库）。附加认证数据绑定 `user_id:platform` —— 把 A 的密文挪到 B 名下会直接解密失败，防的是数据库被改写后的串用。

### 可选同步：服务器单向权威

对服务端记录，App 本地保留「已下载路径」和「收藏」，同步时合并而非覆盖；删除走 tombstone。手机直接提取的记录独立保存在本地，不上传到服务端。

## 已知限制

- 抖音 Web 接口反爬改得很勤，`douyin.py` 是全项目最脆的一块。手机端遇到作品详情 HTTP 403 会用 Android 浏览器内核重试；若网络或平台继续拒绝，需根据 App 显示的具体步骤排查
- 抖音扫码登录走不通，只能导入 cookie
- SQLite 写事务通过 `BEGIN IMMEDIATE` 串行分配同步游标；当前仅验证 SQLite，切换其他数据库需重新设计与验证提交顺序
- 相同平台/视频自动去重；Chromaprint 可提示跨平台相似候选，但片段剪辑、静音、较大起始偏移不保证识别，不自动删除来源
- Android 构建通过、接口字段契约已校验；尚未做真机/模拟器交互和 Room 迁移实测，不能用编译通过替代实机验收
- 手机端仅处理公开可访问作品；抖音/B 站接口及风控可能变化，登录专属作品不支持。手机抽取视频内 AAC 音轨时无损封装成 M4A，其他视频音频编码暂不支持
- **合规**：扒 B 站 / 抖音音频两边 ToS 都不允许。自用风险不大，做成多用户服务或再分发则不然
- 博主批量的抖音主页依赖 Playwright + Chromium 和登录 Cookie；未安装、遇到验证码或出口 IP 被风控时返回 503，真实账号/出口未验收
- 图文配乐按 `music.play_url` 或 `video.play_addr*` 判定；两者都没有的作品仍会被跳过（没有可下载音频）


## 分类与相似音频

默认使用本地规则，`classify_stage=rules`。服务端可在 Git 忽略的 `.env` 中配置 `ARK_API_KEY` 启用[火山方舟 Chat Completions](https://docs.volcengine.com/docs/ark/chat-api?lang=zh&redirect=1) 分类；`GETAUDIO_ARK_MODELS` 是按先后顺序尝试的模型 ID 列表，默认先 `doubao-seed-2-0-mini-260428`，失败再试 `doubao-seed-2-1-pro-260915`。这两个模型已经用当前账号实际调用验证；[模型目录](https://docs.volcengine.com/docs/ark/model-list?lang=zh)中出现不等于账号已开通。还可设置 `GETAUDIO_OLLAMA_MODEL` 使用本地 Ollama 后备；所有 AI 路径失败时回退规则。只有有效且符合分类 schema 的回答会标记 `ai`，`has_vocal=null` 表示没有足够证据。API Key 不放进 APK，因此手机直提取只做本地保存，不调用方舟分类。

```bash
# 为旧音频补分类（默认最多 100 条）；重算已完成 AI 分类可加 --force
.venv/bin/python -m getaudio.cli classify --limit 100
# 为旧音频补指纹，列出相似候选；不会删除或合并记录
.venv/bin/python -m getaudio.cli duplicates --backfill --limit 500
# 逻辑删除指定条目：手机下次同步接收 tombstone；服务器文件保留
.venv/bin/python -m getaudio.cli delete 123
```

新提取音频会自动分类并计算指纹。指纹使用前 120 秒，缺少 Chromaprint 的 ffmpeg 会跳过并记录日志。Android 显示类别和人声判断，搜索框可搜类别，平台、搜索和收藏条件可组合。v1→v2 数据库升级保留收藏；下载使用文件大小和 SHA-256 校验，源音频变更后重新下载。

## 音频 Agent 与手机号账号（0.5.0 历史说明）

「我的」头像入口支持中国大陆手机号＋密码注册、登录和退出。手机号统一规范化为 `+86`，数据库唯一约束保证 `138…`、`+86138…`、`0086138…` 对应同一账号；已注册号码不能重复注册。此版没有短信归属验证、验证码登录或忘记密码流程，不能把“输入手机号”当作已验证手机号。账号与抖音/B站平台登录分别管理。个人会话和记忆按账号隔离；音频库仍使用现有共享服务器库，手机文件仍在本机，旧访客偏好不会凭手机号自动认领。

进入「我的 → 音频助手」，可以：

- 发送抖音/B站分享链接，模型准备待确认提取操作。用户点击「手机提取」或「服务器提取」后调用现有真实提取器，不由大模型直接下载音频，也不保证解除平台 403。
- 接着问本次操作为什么失败，模型读取最近的会话和实际工具结果。手机报告标记 `device_reported`；服务器成功需匹配该用户、该链接的真实成功任务，标记 `server_verified`。确认操作只允许执行一次，重复回传同一结果幂等，不能覆盖已保存结果。
- 根据手机本地曲目和共享服务器库推荐音频。手机发送最多 100 首本地曲目的元数据，不发送音频文件。模型只能引用候选曲目的 ID。
- 明确说“记住…”可得到待确认的长期偏好建议，填入偏好后点击保存才写入。偏好可修改或删除，修改需要 revision，版本记录追加保存；检索只读取当前未删除版本。
- 返回最近会话、开新会话、删除当前会话。删除会话不删除音频或长期偏好。会话接口返回最近 30 个会话，手机展示最近 5 个入口；单会话返回最近 100 条记录，模型只接收最近 16 条记录及最多 50 条当前偏好。

借鉴 `WorkPlan/agent-memory` 的身份边界、当前版本检索、追加版本记录、工具证据和幂等处理设计；没有引入其 PostgreSQL/向量检索基础设施。此版采用 SQLite 和有界会话上下文，适合当前单机项目。历史对话是短期上下文，明确保存的偏好是跨会话长期记忆。模型按 `GETAUDIO_ARK_MODELS` 列表依次尝试，所有模型失败时明确降级为链接提取入口，不假装已完成任务。`ARK_API_KEY` 只在服务端 `.env`；账号凭据不会发给模型，明显的 Cookie/Key/密码输入被拒绝。

登录会话使用独立的 `X-GetAudio-Session` 请求头，以兼容 nginx 的 Basic 访问凭据。密码使用带随机盐的 scrypt，服务端只保存令牌 SHA-256；令牌有效期 30 天，退出后撤销当前令牌。Android 使用 Keystore AES-GCM 加密会话令牌和待同步工具结果，只向登录时绑定的服务器发送令牌；账号登录要求 HTTPS（debug 回环开发例外）。登录接口有单进程每 IP 五分钟 20 次的限流，不是多进程全局限流。

注册账号 ID 在旧记忆、平台凭证和提取接口中也必须由同账号会话授权；旧版访客 ID 仍用于兼容，不能当作账户身份认证。旧 API 不应脱离 nginx 访问控制直接暴露。新表启动时自动创建，既有音频表结构保持不变。工具结果若网络回传失败，手机加密保存回执，重新进入助手可点击「同步提取结果」，不会再次下载。若进程在提取完成、落回执之前被结束，会话显示“已开始”，需要检查音频库后再决定是否重新发送链接。


## 定时抓取

```bash
.venv/bin/python -m getaudio.cli crawl --check           # 只校验 YAML，不触网
.venv/bin/python -m getaudio.cli crawl --once            # 执行到期任务一轮
.venv/bin/python -m getaudio.cli crawl --once --force    # 忽略到期时间
.venv/bin/python -m getaudio.cli crawl                   # 每 30 秒检查到期任务
```

`keywords` 使用 yt-dlp 的 `bilisearch`（只搜索 B 站），`urls` 可填写 B 站或抖音分享链接。`top_n` 是每组每轮的总提取上限；关键词结果交错选取并去重。周期支持 `m/h/d`，可设置 `enabled: false` 暂停某组，`user_id` 指定提取凭证。

```yaml
groups:
  - name: 我的链接
    interval: 12h
    top_n: 5
    urls:
      - https://www.bilibili.com/video/实际BV号/
    enabled: true
```

调度状态写入 `crawl_state`，重启保留进度；部分失败不妨碍其余链接，失败组最多五分钟后重试。同一临时目录上的多个 worker 用文件锁互斥。只支持单机工作目录共享场景，不是分布式调度。使用独立 worker，不在每个 Uvicorn 进程里重复启动。

## 运行与部署

提供 `deploy/` 下的 systemd 模板，默认路径为 `/home/ubuntu/project/GetAudio`、用户为 `ubuntu`。按机器实际情况调整后安装；开发过程没有自动启用常驻抓取，也没有批量下载默认关键词结果。API 模板默认监听回环地址，手机访问需配置可信内网入口。账号与新 Agent API 已有会话鉴权；共享音频及旧访客接口仍依赖 nginx 访问控制，不应直接暴露到公网。

首次启动会自动新增调度、指纹表，不修改原 tracks 列。备份应包含 SQLite 数据库（使用 SQLite backup 方式取得一致快照）、音频目录和加密密钥；丢失密钥后凭证无法恢复。

## 0.9.0 批量提取、自定义背景与导入

- **批量提取**：一个输入框粘贴即识别，`LinkScanner` 从 `http(s)://` 或裸域名起做最长匹配，遇到空白、中文、全角标点和引号即停；按规范化地址或 `(platform, key)` 去重，短链用路径末段（形如 `短链:jku1JAdzpCY`），避免多条短链被当成同一条。多条先列清单确认，再串行执行，单条失败不影响后续，结束时留结果卡。批量模式隐藏只支持单条的「从服务器提取」。
- **自定义背景**：相册图走 `OpenDocument` + `takePersistableUriPermission`，重启仍有效；内置图不联网。卡片、按钮保持不透明保证可读性，卡片不透明度单独可调。
- **导入本地音频**：系统文件选择器多选 `audio/*`，复制进 `filesDir/audio/<id>.audio`，id 由内容 sha256 派生为负数，与云端 id 不冲突，重复导入直接跳过；`platform = "local"`，不参与云端同步。用途是换签名/重装前导出、装好再导入。
- **B站 412 加固**：`api.bilibili.com` 对没有 `buvid3` 的请求直接回 412，新增 `refreshBiliCredentials()` 从 `x/frontend/finger/spi` 取 `b_3`/`b_4` 写入两个域，412 时刷新一次并重试一次；Cookie 域必须 `trimStart('.')`，否则 OkHttp 抛 `unexpected domain`。

实现细节与踩坑见 [0.9.0 批量提取、背景与导入](docs/batch-extraction-and-background-0.9.0.md)。

## 0.9.6 拖动返工与内置壁纸

- **拖动返工（0.9.5 的修法是错的）**：旧版把贴边自动滚动的像素补进被拖行中心，手指不动中心却一直漂，漂出视口后退化成「取最近边缘行」——第一条往下拖会直接窜到第 30 条；跨多行换位又让布局重排、下一帧判到反向，末条往上拖时剧烈抖动。现在：中心只跟手指走（`scrollBy` 不再回写）、判定夹在可视区内、只和紧邻的上下行比、越过中线也只挪一格，目标行不可见时宁可不动。
- **拖动判定抽出纯函数** `reorderStep()` 并补 6 项单测（30 行模型：一格一格推进、贴边滚到底、末条上拖无反向、中心不动不再换位）。
- **内置壁纸**：13 张静态（长边 1280 JPEG）、3 张动画 WebP、3 段 1080×1920 循环视频，全部打包在 `assets/backgrounds/`，外观页两排缩略图直接点选，不联网不申请权限。
- **静音是硬性的**：内置视频编码时就去掉音轨（`-an`），自选视频 `volume=0` 且不申请音频焦点，动图本身无音轨。
- 2026-10-28 实测：GetAudio 81 项单测通过（新增 6 项拖动判定）、Lint 0 errors / 28 warnings，debug/release 构建成功，同签名原地升级到 0.9.6（code 34）；真机确认 13 张静态与 6 张动态缩略图渲染正常、视频与动图背景都能播放、无崩溃。30 条真实队列的拖动手感仍需真机复验。

## 0.9.7 拖动第三次返工与壁纸取景

- **拖动返工（0.9.6 的修法仍是错的）**：0.9.6 让被拖行留在列表里、用 `translationY` 补偿自己槽位的位移，可补偿量是按上一帧的槽位算的 —— 换位那一帧 `draft` 已变、布局还没跑，行先跳一下再跳回来，就是「疯狂抖动」；同时中心被夹在可视区后判定退化成「见谁换谁」，一帧一格地连换，第一条往下拖就窜到第 26–30 条。
- **现在的做法**：被拖行移出列表，画在浮层里，位置只由手指坐标决定；列表原位留等高的占位块；落点 = **手指当前所在的那一行**，且只从可视行里选，目标天然被夹在屏幕内，任何一帧都不可能跨出可视区。
- **判定函数换成 `dropTarget()`**，8 项单测（30 行模型：首条下拖一格一格、贴底续滚 30 条不丢、末条上拖无反向、手指不动不换位、任意 y 都落在可视区内）。
- **壁纸取景**：外观页新增「显示区域 → 调整显示区域」，9:19.5 选框 + 旋转 90° + 双指缩放 + 单指平移 + 整张/铺满/复位。原图是 16:9 横图，铺满竖屏只露 26% 宽、人物常常只露一半甚至看着是倒的，现在自己选。
- **静态壁纸重出**：长边 1280 → 2200（q76），转 90° 后在 1440 宽的屏幕上只放大 1.16 倍；APK 27 MB → 32.7 MB。
- 2026-10-28 实测：GetAudio 92 项单测通过（8 项拖动判定 + 9 项取景几何）、Lint 0 errors / 28 warnings，debug/release 构建成功，同签名原地升级到 0.9.7（code 35）。

## 0.9.8 库页手动排序拖动修复与下载失败上报

- **用户说的「第一条往下拖立刻跳到最后」其实在库页**：不是播放队列面板，而是音频库「手动」排序的 `LibraryTrackList`。它自己另写了一套拖动：被拖行留在列表里做 `translationY` 补偿，落点直接拿屏幕坐标去命中行。`LazyColumn` 每次换位都会把第一个可见项钉在原像素上，槽位坐标整体平移，于是判定每帧都指到后面几行 —— 首条一路窜到末尾。
- **现在和队列同一套模型**：被拖行移出列表画浮层、原位留等高占位；判定改用 `dropTarget(from, 槽位中心 + residual, slots, inset)`，换位后 `residual` 只保留「手指落在新一行里的偏移」，不再用会漂的屏幕绝对值。
- **顺带修掉移植时暴露的第二个 bug**：手势原来挂在每一行的 `pointerInput` 上，可拖动一开始这一行就被换成占位 `Spacer` 离屏，手势节点跟着销毁 —— 第一次换位后拖动就断（真机表现为「拖一下就自己停下」）。检测器改挂 `LazyColumn`，`onDragStart` 用 `visibleItemsInfo` 命中最近一行。
- **下载失败自动上报**：原来只有「手机直提取」失败进失败报告队列，库内下载（手动下载 / 加入播放列表 / 播放前缓存）失败只弹一句提示，服务器查不到。现在 `download()` 失败也会带「阶段 / HTTP / 已收字节 / 期望字节 / 耗时 / 主机」入队并唤醒上传，同曲目同错误 10 分钟内只报一次。
- **媒体下载更抗断流**：每个地址最多重试 3 次（仅 `IOException`），带 `Connection: close` + `Accept-Encoding: identity` 每次走新连接，日志记「已收 N 字节」。`SocketException` 等错误改中文提示（原来是直接把英文 `software caused connection abort` 弹给用户）。
- 2026-10-28 实测：GetAudio 95 项单测通过（11 项拖动判定 + 9 项取景几何）、Lint 0 errors / 27 warnings，debug/release 构建成功，同签名原地升级到 0.9.8（code 36）。真机 1440×3200 / Android 14 上用 `input draganddrop` 长按拖动首条：只移动一格（编号 1 → 2），没有跳到末尾；重启进程后顺序仍是新的，说明已落库。服务器回查确认 0.9.7 的三条提取失败报告都在（`媒体下载 1/1：SocketException`），提取上报链路本来就是通的。

## 0.9.9 库页拖动：视口不再被列表自己推走

0.9.8 之后用户复现了更细的两个毛病：「第一条往下拖，文件跟着手指走，但它原来那块变空；拖到 7、8 之间，画面还停在最上面」；「把别的项拖到第一条再拖回来往下移，第一条的位置会留下一大段透明空白，序号也乱」。抓日志（临时 `Log.d` + 真机 `input swipe` 慢速拖动）后确认是两件独立的事：

- **列表自己在滚**。`itemsIndexed` 带了 `key`，`LazyColumn` 换位时会把「第一个可见项」按 key 钉回原像素 —— 拖第一条时第一个可见项正是被拖行，于是每换一格列表就自己往下滚一行（日志里 `firstVisibleItemIndex` 一路 0→1→2）。画面被推走、占位行留在原地，就是「顶部空一大块」「拖到 7、8 之间还停在最上面」。改成 `itemsIndexed(draft)` **不传 key**：key 退化成下标，换位不改变下标，列表永远不会自己滚。代价是行按位置复用（行内没有按曲目记忆的状态，实测无副作用）。
- **相邻行高度不一样会来回换**。标题两行 / 三行的行高不同（283px vs 353px），换位后布局重排，手指正好停在「换过去、换回来都说得通」的重叠区，于是每帧来回换一格（日志里 `from=3→4→3→4…` 连续十几次）。加了**反向换位死区**：换位后要再移动半行（`0.5 × min(被拖行高, 目标行高)`）才允许换回去；同向换位不受影响，快拖依旧跟手。
- 判定顺势简化：列表不再自己滚，就不需要再记「自上次换位以来的手指位移（`residual`）」，直接用手指在视口里的真实纵坐标 `dropTarget(from, pointerY, slots, inset)`。队列面板同一套改动。
- 2026-10-28 实测（1440×3200 / Android 14，0.9.9）：首条下拖两行 → 占位行始终在手指下面、顶部由下一行补齐、序号 1..5 连续；拖第 5 条到第一条 → 占位行一路跟到第 1 格、顶部不空；再把第 1 条往下拖回第 4 位 → 无透明空白、无序号错乱；`am force-stop` 重启后顺序保持。单测 98 项（14 项拖动判定：新增「占位行始终在手指下面」「换位不让列表自己滚」「带 key 会滚走」「行高不等不在静止手指下反复换位」等）、Lint 0 errors / 27 warnings。
