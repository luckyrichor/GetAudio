# 0.8.2：B站手机直提取 HTTP 412 修复

## 现象与原因

REDMI K80、GetAudio 0.7.0 手机直提取公开B站链接时报“平台请求失败 HTTP 412”。短链接展开成功。分步骤真机诊断确认：首页预热、访客接口和作品信息均成功，失败发生在带WBI签名的播放地址接口。该请求由手机普通HTTP客户端发出；相同播放请求切换到Android WebView浏览器上下文后返回200。能够确定请求上下文影响该平台响应，不能据此声称已定位到具体IP、TLS指纹或Cookie算法。

多分P不是此次412的直接原因，但音轨必须按p选正确cid。用户提供视频 `BV1KG411w7r2` 有6个分P，P3是“气荡山河”（cid 1466791237），P5是“龙年中秋”（cid 25986073823）。提取选中分P的音轨，不批量下载整个合集，也不回退P1。

## 修复与调用

`DirectExtractor.bilibili` 继续先请求作品信息、按pages[p-1]读取cid，并签名请求播放接口。仅HTTP412启用 `BilibiliBrowserAudio.fetch`：

1. 校验页面域名为www.bilibili.com，API域名为api.bilibili.com且路径为/x/player/wbi/playurl。
2. 创建WebView，阻止非允许HTTPS源的主框架跳转，脚本执行前重新核对页面源；API fetch禁止重定向。启用脚本和DOM存储、关闭文件及内容访问，加载同一视频及分P页面。
3. 在浏览器上下文内fetch同一已签名URL，包含原cid。仅重试一次，总等待上限30秒。
4. 只接受HTTP200并继续原业务code/DASH音轨校验；401/404等不会触发这条备用路径。失败明确提示平台仍有限制，不伪造成功。
5. 无论成功、超时或取消，都停止并销毁WebView。提取继续使用原下载、大小校验、AAC封装与入库流程，不修改账号会话、服务器授权或AAC预热帧策略。

首页及访客预热是可选Cookie准备，失败记日志后继续必需的作品请求；取消会立即停止，不吞取消异常。必需接口错误仍保留。日志只记录步骤、状态码和文件大小，不记录Cookie、GetAudio令牌或播放URL。

## 分P、编号与去重

分享短链展开后保留p；没有p使用P1，无效页码拒绝。分P使用独立key：P1为BV号、P2及以后为BV号-pN，映射为稳定负本地ID。不同分P不覆盖，重复同一分P沿用编号。P2及以后标题附P编号和子标题；既有改名、云端曲目和播放列表策略保持。

## 验证证据

基线GitHub在开发期间新增0.8.1功能，先快进合并bd4aa63，再将本修复升级为0.8.2/code21；保持手机号与平台绑定功能。同包名com.getaudio.app、同原签名升级，保留私有配置与已有音频。

- 新增5个JVM测试：可选预热失败不阻断必需API、必需失败仍抛出、取消停止、备用请求只限412、HTTPS导航边界。测试先缺少实现失败，补实现后全部通过。
- Android全JVM **54项通过**；debug/release构建成功，Lint零错误（10警告、1提示）；无需改服务端提取逻辑。
- 真机捕获普通播放请求412→浏览器请求200→DASH音轨3个候选→CDN200→M4A保存→本地入库。
- 手机数据库核对P3与P5均为独立local负编号，P3实际约37.059秒、P5约34.992秒，文件分别367577与366816字节。另一个云端P3是原账号记录，保留用户已有命名。
- 用户确认成功，并又下载一个新音频；媒体会话显示GetAudio正在播放、error=null。用户在验证期间切换了分P/分享链接，因此不把某一次短链解析结果硬套到另一次提取日志。

## 限制

此次验证覆盖上述多分P公开视频和用户新增提取，不承诺所有平台风控均可恢复。浏览器备用请求仍可能被平台拒绝、超时或受到作品权限限制。此版不绕过付费/私有资源权限，不把失败归咎于USB连接，也不要求用户提供共享服务器密码。
