# 退出后恢复播放列表与进度（0.8.5）

## 原因与行为

此前播放列表顺序保存在 Room 中，但 `PlayerHolder` 的队列、当前索引和播放模式只是进程内状态，`PlaybackService` 每次创建空播放器。新启动没有主动加载列表，底部栏又只在队列非空时显示，因此必须重新选择歌曲。

现在进入应用时恢复上次列表、当前歌曲、播放位置及播放方式。冷启动默认暂停，点击底部继续按钮即可接着听；已连接且有内容的播放会话保持运行，不会因再次打开页面而暂停或跳回。

## 保存与恢复链路

- 新增应用私有 SharedPreferences `playback-memory` 的 `last` 记录，保存 `playlistId`、`trackId`、`positionMs`、`mode`；不保存文件路径或凭据。
- 服务监听播放器事件，并每秒保存播放位置；Activity 停止、任务移除、服务销毁时同步落盘，减少退出窗口的进度损失。强制杀进程不保证有生命周期回调，恢复位置可能有约一秒误差。
- 启动时 `PlayerHolder.restore` 先刷新账号可见范围，随后通过队列互斥锁与添加、删除、排序操作串行。
- Room 中该列表的引用与排序为准，按 ID 匹配当前曲目，不沿用旧索引，所以拖拽排序不会导致恢复到另一首歌。
- 只恢复当前账号可见、已存在本地且非空的文件，不自动联网下载。数据库查询与控制器连接后再次核对账号及服务器，避免切换期间恢复旧范围。
- 恢复到已保存进度；已知时长时限制在有效范围。原歌曲已删除或本地文件缺失时选剩余第一首，从零开始；全无可用曲目则清空旧恢复记录及残留队列。
- 保存记录损坏时忽略。没有历史记录的旧版本首次升级，回退到已有默认列表的第一首；旧版未记录的进度无法追溯。之后使用会记录实际选择。
- 持久化列表排序不变，音频文件及元数据不变；无新增服务器接口或数据库迁移。
- 定时停止仍是原有会话内设置，本次不增加跨进程定时恢复。

实现前因缺少实现编译失败；实现后全部 69 项 JVM 测试通过。最终 Debug/Release 构建与 Lint 结果、真机记录见下方交付验证。

独立代码审查发现并修复“队列单例仍非空但播放服务已断开时跳过恢复”的边界，恢复前需要同时满足连接有效且 Media3 队列非空才能复用。
