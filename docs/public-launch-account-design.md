# GetAudio / GetVideo 面向公众开放：账号、同步与服务器安全设计方案

> 文档状态：**设计稿，未实现**，供评审用。
> 适用范围：GetAudio（音频）与 GetVideo（视频）两端同源客户端 + 各自 Python 服务端。
> 阅读对象：熟悉本项目的评审 Agent。本文不重复项目背景，只写「面向公众开放」需要新增/改造的设计。
> 文中 `路径:行号` 均指当前仓库代码，作为设计依据的出处。
>
> **修订 v2（2026-10-28 晚）：预算约束更新。** 明确约束：**不买域名、不配 CDN、不做 ICP 备案、不接短信计费、只有这一台机器（4C/7.5G/118G 盘）且只用到明年**。本版**全文重写**了与零预算冲突的部分：域名/CDN/WAF → remote_config（GitHub 多路）+ LE IP 证书 + Host 伪装；短信验证码登录 → 邮箱+密码 + SMTP 验证；Postgres/Alembic → SQLite WAL + 自建版本化迁移；对象存储/付费档 → 本地盘 blob 池 + per-user 配额 + 来源索引重提兜底；备份 → age 加密推 GitHub 私库。新增了单机容量上限（音频 ~250 人/视频 ~30 人）、无备案的合规缺口声明、一年期 EOL 与重建手册。评审时以 v2 内容为准。

## 1. 目标、范围与成功标准

### 1.1 目标

让不特定数量的真实用户能注册、登录、在**多台设备**上使用，并在换设备后把**音频/视频文件本身和改过的元数据**（重命名、分类、排序、删除）同步回来。

### 1.2 范围内 / 范围外

| 范围内 | 范围外（本期不做，但要留接口） |
|---|---|
| 邮箱+密码登录（老手机号入口只保留一个迁移期）、会话与设备管理 | 支付与套餐结算（零预算下连付费档也不做，只做配额与用量展示） |
| 多设备登录、踢下线、登录历史 | 内容社区、分享广场、公共链接 |
| 元数据双向同步（增删改排序） | 跨平台（iOS / Web） |
| 音频/视频文件云端备份与按需下载 | AI 分类与指纹（沿用现有，不扩） |
| B 站 / 抖音账号绑定的产品与安全设计 | 直播、弹幕、评论等平台互动能力 |
| 隐藏源站 IP、收敛暴露面、服务端加固 | 服务器端转码多码率 |
| 合规地基（隐私政策、注销、合规缺口声明） | 国际化 / 多语言 |

### 1.3 成功标准（可验收）

1. 新用户 3 分钟内完成注册（含邮件验证等待）并登录成功。
2. 换设备登录 → 点「同步」→ 元数据 30 秒内到位；文件按用户选择逐条/批量下载，进度可见、可中断续传。
3. 两台设备同时改名/拖动排序，收敛后两台一致，无丢失、无重复。
4. 任意账号 A 的请求无法读到账号 B 的元数据或文件（自动化越权用例全绿）。
5. 反编译 APK 拿不到源站 IP（只有 GitHub 上的 remote_config 地址）；不带正确 Host 头的访问与端口扫描得到 444 空响应；IP 变更无需发版即可切换。
6. 单用户成本可预测：存储与流量有上限、可计量、可限速。

## 2. 现状约束（为什么必须改造）

| 维度 | 现状 | 对公众开放的阻碍 |
|---|---|---|
| 登录方式 | 手机号 + 密码（`ui/screen/AccountScreen.kt:102`），密码 ≥8 位；无验证码、无找回密码 | 密码是面向公众的最大成本（找回、泄露、撞库），必须补验证码与找回 |
| 密码哈希 | scrypt n=16384/r=8/p=1 + 16B 随机盐（`getaudio/accounts.py:41-49`） | 算法可接受，参数偏低；建议升级 argon2id 或提高参数 |
| 会话 | `app_sessions` 仅存 `token_hash + user_id + expires_at`，30 天，无 refresh、无设备表（`models.py:189-193`、`accounts.py:104-110`） | 无法做多设备管理/踢下线/异常登录识别；token 一旦泄露要 30 天才能失效 |
| 鉴权 | `X-GetAudio-Session` 头（`accounts.py:71`）；v2 接口按 `owner_scope` 过滤 | **老接口 `/extract`、`/sync`、`/tracks` 本身无应用层鉴权，靠 nginx Basic Auth**（`account_api.py:1`）—— 公众开放必须收敛 |
| 同步方向 | **单向**：服务端 → 手机，只拉元数据（`TrackRepository.kt:178`、`sync/SyncWorker.kt`） | 手机直提取的结果、用户在手机上改的名字，都上不去 |
| 文件上传 | **完全没有上行接口**（全库无 Multipart/分块上传） | 换设备拿不到文件，需求 2 无法实现 |
| 游标 | 全局自增 `updated_seq`（`db.py:55-62` max+1，SQLite `BEGIN IMMEDIATE` 串行化） | 全局热点 + 泄露全局活跃量；客户端 `updatedSeq` 语义混杂（`AppDatabase.kt:40` 注释：旧版是毫秒时间戳），必须重置 |
| 主键 | 服务端 `tracks.id` 自增 int；客户端云端 id 为正数、本地为负数（`AccountScope.kt:10`、`Entities.kt`） | 离线新建 + 多设备合并会撞号，必须换客户端生成的 UUID |
| 删除 | 客户端靠独立表 `deleted_tracks`（`Entities.kt:81`）；服务端 `tracks.deleted` 软删标记 | 缺统一 tombstone 与 TTL，删了又同步回来/永久丢 |
| 排序 | 服务端 1..N 重编号（`docs/library-sort-and-editor-0.9.x.md`） | 拖一次动 100 行 = 100 条同步 + 高冲突概率 |
| 文件存储 | 本地磁盘 `data/audio`，按 `owner_scope` 分子目录（`storage_scope.py:18-20`）；`audio_sha256` 只记录不去重 | 无法扩容/多机；存储成本失控 |
| 数据库 | SQLite（`config.py:15`），无 Alembic，只有一次性迁移脚本（`schema_migrations.py`），**无备份脚本** | 多用户并发写串行化；改表靠手工；无备份等于没有数据 |
| 限流/审计 | 仅登录类有进程内存级 per-IP 限流（`accounts.py:76-91`）；**无审计日志** | 无法防刷、无法追溯安全事件 |
| 平台绑定 | B 站：扫码拿 Cookie → AES-256-GCM 加密入库（AAD 绑定 `user_id:platform`）；抖音：OAuth 只存 open_id（`platform_accounts.py`、`crypto.py:92-93`） | 机制基本正确，缺状态机、失效检测、使用配额与风控 |
| 服务器地址 | **客户端硬编码 `https://43.142.37.199/`**（`ServerConnectionPolicy.kt:5`），设置页只有一个「服务器地址」输入框（`ServerSettingsDialog.kt:50`） | 反编译即得源站 IP；UI 隐藏无意义。零预算下无域名/CDN 可换，改为 remote_config 间接下发 + 换 IP 不发版（8.1） |
| 可观测 | 无崩溃上报、无埋点、无推送 | 公众版无法定位线上问题 |

## 3. 总体架构（零预算单机版）

```
┌──────── 客户端（Android） ────────┐
│ 登录(邮箱+密码) · 设备列表        │
│ Room(本地库, 权威副本) ─ SyncEngine│
└──── HTTPS 直连单机（443） ─────┘
              │
┌──── 单机 tx：nginx + FastAPI ────┐
│ /v2/auth /v2/devices              │
│ /v2/sync(双向) /v2/files          │
│ /v2/extract · 配额 · 审计 · 限流  │
│ SQLite(WAL) + 本地磁盘 blob 池    │
└──────┬───────────────────────┘
       │ 每日 age 加密快照推送
┌─ GitHub（免费间接层，穷人的域名） ─┐
│ remote_config(服务器地址/开关/最低版本)│
│ APK 分发 · 数据库加密备份          │
└──────────────────────────────┘
```

关键变化（相对现状）：

1. **不引入域名/CDN/WAF/Postgres/对象存储** —— 零预算与单机约束下全部放弃；相应风险转入 §15 风险登记册，缓解手段是「服务加固 + 可迁移」而不是「隐藏」。
2. **SQLite 保留**，开启 WAL；换 `BEGIN IMMEDIATE` 全局 seq 为 per-user seq（见 5.2）。写路径在几百用户量级完全够用；SQLAlchemy 抽象保留，Postgres 作为「换机时顺手可做」的可选项，不在本期内。
3. **新增上行链路**（上传 + 秒传 + 断点续传），同步由单向变双向 —— 这与预算无关，是需求 2 的本体。
4. **blob 存本地磁盘**：设全局池上限（当前盘剩 ~28 GB，见 §10）+ per-user 配额，不引对象存储。
5. **remote_config 引导放 GitHub**（raw / jsDelivr / Release 附件多路兜底）：APK 里不再硬编码唯一 IP，只硬编码这份配置的地址。IP 变更、端口调整、功能开关、最低版本，都只改一个文件，不发版。
6. 监控告警用免费方案（GitHub Actions 定时探活 + ntfy/Bark 推送；详见 §8.4）。

## 4. 账号体系设计

### 4.1 登录方式选型 【决策】

零预算约束：**短信按条计费、需签名报备；微信/Apple 登录需企业资质** —— 全部出局，本期只考虑免费方案。

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 手机号 + 密码（现状） | 零成本 | 找回难、撞库 | 保留为兼容入口 |
| **邮箱 + 密码（主推）** | 免费（QQ 邮箱/163 SMTP 即可发验证邮件）、可找回、可做登录提醒、邮箱本身不必然绑定实名 | 国内用户注册多一步（没有邮箱的要现注册） | **采用** |
| 用户名 + 密码（无邮箱） | 转化最高 | 无法找回，纯客服灾难 | 不做（邮箱为必填） |
| 手机号 + 短信验证码 | 体验最好 | 按条计费 + 签名报备 + 防刷成本 | **留作将来有预算后的升级项**，表结构预留 `phone` 字段 |

**设计：主登录 = 邮箱 + 密码；注册需邮箱验证链接（防乱填、防机器）；现有手机号+密码入口保留一个版本周期用于老用户迁移，之后引导绑定邮箱。**

> 邮箱在国内的渗透率不如手机号，这是免费方案的真实代价；缓解办法是支持 QQ 邮箱这类「人人都有」的服务商，并在注册页放「没有邮箱？」说明。

### 4.2 邮箱验证与防刷

- **验证方式**：注册/找回/敏感操作发 6 位数字验证码或确认链接，15 分钟有效，单码最多校验 5 次。
- **发送通道**：免费 SMTP（QQ 邮箱 / 163 邮箱），个人号每日发信上限只有几十到几百封（随服务商与账号信誉浮动）—— 上限本身是天然的成本熔断，也是单机小规模的自然闸门。
- 频率限制：同邮箱 60s 间隔、每日 5 封；同 IP 每日 30 封；同设备每日 10 封。
- 人机校验：触发条件下的行为/图形验证码用免费方案（自建简单挑战即可，如滑块），或暂缓——先靠限流顶着，观察被刷情况再决定。
- 黑名单：一次性邮箱域名（10minutemail 等）可配置拒收或标记观察。
- `mail_logs` 表记录（邮箱哈希、IP、设备、模板、结果），用于回溯与「这个邮箱是不是被刷了」的判断。
- **零成本收益**：邮件不花钱，被刷最坏后果是 SMTP 配额耗尽（当天注册暂停），不会造成现金损失。

### 4.3 凭据存储

- 密码（保留期内）：**argon2id**（m=64MB, t=3, p=4）替换现有 scrypt 参数；登录失败走 dummy hash 校验（现状已有，`accounts.py:52`），保留。
- 手机号：库内存 `phone_e164` + `phone_hash`（HMAC，便于风控比对），展示时脱敏。
- 平台 Cookie：维持**仅服务端加密存储**（AES-256-GCM，AAD 绑定 `user_id:platform`，现状已对），新增：密钥从独立环境变量/密钥文件注入（零预算无 KMS），**与数据库分开备份**；支持密钥轮换（多版本 key_id）。

### 4.4 会话与多设备（需求 2 的地基）

**令牌设计**

| 令牌 | 形态 | 有效期 | 存储 |
|---|---|---|---|
| access_token | 不透明串（`secrets.token_urlsafe(32)`，沿用现状风格） | **2 小时** | 客户端内存 + Keystore 加密落盘 |
| refresh_token | 不透明串 | **90 天，每次刷新轮换** | 服务端只存 `sha256`；客户端 Keystore |

- **轮换即作废**：刷新时旧 refresh 立即失效；若检测到已失效的 refresh 被再次使用 → 判定泄露，**吊销该设备及其家族令牌**并要求重新登录。
- 沿用 `X-GetAudio-Session` 头（现状），但语义拆成 `access`；刷新接口单独路径并限速。

**设备表 `devices`**

| 字段 | 说明 |
|---|---|
| `id` / `user_id` / `device_id` | `device_id` 由客户端生成 UUIDv4，存 Keystore，卸载即失效 |
| `device_name` | 型号 + 系统版本（用户可改别名） |
| `last_ip` / `last_ua` / `last_seen_at` | 登录历史展示 |
| `app_version` / `platform` | 灰度与兼容判断 |
| `status` | `active / revoked` |
| `created_at` | 用于「最旧设备先踢」 |

**能力清单**

1. 并发设备数上限：默认 **5 台**（可配）。超出时策略【决策】：`拒绝新登录`（更安全）或 `踢最久未活跃`（体验好）。建议：**默认拒绝 + 提示去设备列表清理**。
2. 设备列表页：别名、型号、最后活跃时间/IP 属地、当前设备标记、逐台「退出登录」+「退出全部」。
3. 登录历史（近 30 条）+ 新设备登录提醒：无推送能力 → 在下次启动/进入「我的」时弹一次「新设备于 X 登录，若非本人请修改密码并踢出」。
4. 敏感操作二次验证：改绑邮箱、注销账号、解绑平台、退出全部设备 → 邮箱验证码。
5. 长期不活跃（180 天）refresh 自动过期，需重新登录。

### 4.5 账号生命周期

- **注销**：App 内可见入口（合规硬要求）。流程：二次验证 → 立即停用 → 15 个工作日内物理删除（元数据、blob、平台凭据、审计脱敏保留）。给出「导出我的数据」按钮（JSON 元数据 + 可选音频包）。
- **改绑邮箱**：旧邮箱验证码 + 新邮箱验证码，两次验证中间 24h 冷静期可选；旧邮箱不可用走申诉（注册信息核对 + 人工处理）。
- **账号找回**：邮箱验证码重置密码 —— 邮箱即身份，这正是选邮箱登录换来的找回能力。

## 5. 数据模型与同步（需求 2 的核心）

### 5.1 标识与主键

- **引入 `track_uid`（UUIDv7）作为跨端业务主键**，由**创建方客户端**生成，随创建即固定；服务端保留自增 `id` 仅作内部外键。
  - 理由：离线可创建、多设备不撞号、合并无需映射表。现有「云端正数/本地负数」方案（`AccountScope.kt:10`）在双向同步下必然冲突，废弃。
- **自然键**：`(platform, video_id, page, quality)` —— 同一链接重复提取只产生一条；改名/改分类不产生新条目。现状 `(owner_scope, platform, video_id)` 唯一约束（`models.py:47`）需扩展 `page/quality`。
- 本地导入/剪辑产物同样有 `track_uid`，只是 `source_kind = local`，不参与自然键去重。

### 5.2 变更日志与游标

- 服务端为**每个用户**维护单调递增 `user_seq`（`user_counters` 表，SQLite 单机下事务内 `UPDATE ... RETURNING` 取号即可，不依赖 PG sequence），每次写 `tracks` 时 `user_seq += 1` 并写一行 `track_changes`：

| 字段 | 说明 |
|---|---|
| `user_id` / `seq` | 该用户的变更序号 |
| `track_uid` | 变更对象 |
| `op` | `upsert / delete` |
| `fields` | 变更字段集合（便于客户端只取需要的列） |
| `device_id` / `server_ts` | 冲突裁决依据 |

- 客户端保存 `last_seq`；`GET /v2/sync?cursor=N` 返回 `changes` + `new_cursor`。
- **废弃全局 `updated_seq`**：一是热点，二是泄露全局活跃量，三是客户端语义混杂必须重置（迁移时全量重拉一次）。
- 变更日志保留 90 天；更早的客户端强制全量重拉。

### 5.3 双向同步流程

```
启动时 / 每 6h(WiFi) / 手动：
  1. push: 本地 dirty 队列 → POST /v2/sync/push（幂等，带 client_op_id）
  2. pull: GET /v2/sync?cursor=last_seq → 应用变更（本地无此 uid 则按 op 处理）
  3. files: 计算缺失 → 上传本地独有的 blob / 下载云端独有的 blob
  4. 记录 last_seq、last_sync_at
```

- **幂等**：每次 push 携带客户端生成的 `client_op_id`（UUID），服务端 24h 内去重，避免重试造成重复写入。
- **顺序**：先 push 再 pull，保证本机改动先落地，避免把自己的改动当成远端变更来回应用。
- **节流**：push 批处理上限 200 条/次；失败指数退避；移动网络默认不传文件（用户可覆盖）。

### 5.4 冲突解决

**规则：字段级 LWW + `device_id` 确定性兜底。**

- 每条变更带 `server_ts`（服务端接收时间）与 `device_id`。
- 同一字段冲突：取 `server_ts` 大者；相等时取 `device_id` 字典序大者 —— 保证各端收敛到同一结果。
- **不使用客户端时间**（时钟不可信）。
- 特殊字段：
  - `title/category/cover`：LWW，但保留 `title_edited_by_user` 标记，避免平台刷新覆盖用户改名（现状用户改名是核心诉求）。
  - `sort_key`：见 5.5。
  - `deleted`：删除优先于字段更新，除非对方有更晚的 `restore`。

### 5.5 排序：改用分数索引（fractional index）

现状拖动一次要重排 1..N，双向同步下必然打架。

**设计**：每条记录一个 `sort_key` 字符串（base62 的 LexoRank/frac-index），拖动 = 只改被拖那一条的 `sort_key`（取前后两条中点）。

- 收益：一次拖动 = 1 条变更（现在是 N 条）；两台设备改不同条目零冲突；服务端不必全局重编号。
- 代价：字符串比较排序；需在服务端与 Room 两侧统一比较函数（长度+字典序）。
- 迁移：现有 `sortIndex` 一次性转成等间距 `sort_key`。

### 5.6 删除与回收站

- 删除 = 写 tombstone（`deleted_at` + `seq`），非物理删除。
- 回收站保留 **30 天**，可跨设备恢复；到期任务物理删除（磁盘 blob 池引用计数 -1，引用为 0 才删文件）。
- 服务端 blob 用 `ref_count`，避免同一文件被多条目引用时误删。

### 5.7 文件同步（新增，最大的工程量）

**上传**

1. 客户端算 `sha256` + `size` → `POST /v2/files/precheck` → 命中则**秒传**（直接建引用，不传字节）；未命中返回 `upload_ticket`。
2. `PUT /v2/files/{ticket}`：分块（建议 4 MB/块）+ `offset` 提交，支持断点续传；服务端边写边校验 `size` 上限，超限即断。
3. `POST /v2/files/commit`：校验最终 `sha256`、写入 `blobs` 表、绑定 `track_uid`、`ref_count += 1`。
4. 约束：仅 WiFi 默认开启（沿用 `SyncWorker` 的 UNMETERED 约束）；前台进度通知 + 可暂停；后台 WorkManager 续传。

**下载**

- `GET /v2/files/{uid}/url` → 返回**短期签名 URL（10 分钟）**，客户端走系统下载器/断点续传下载到本地 `localPath`。
- 不使用永久直链。签名 URL 在单机本地盘上用 nginx `secure_link` 模块实现（零成本）：应用签发带过期时间的 MD5 戳，nginx 校验通过才放行 blob 路径；blob 目录 700、禁目录列举。
- 提供「仅保留云端」模式（本地不落盘，播时流式 + 缓存），解决低端机存储不足。

**文件状态机（UI 四态角标）**

`仅本地` → `上传中` → `已备份` ↘ `仅云端` → `下载中` → `已备份`

### 5.8 去重策略（分两级）

| 层级 | 范围 | 说明 |
|---|---|---|
| **内容去重（跨用户）** | 仅限 **平台公开内容**：按 `(platform, video_id, page, quality)` 或 blob hash，全局共享一份 | 源是公开 URL，不存在隐私放大 |
| **内容去重（用户内）** | 用户自己导入/剪辑的本地文件：只在该 `owner_id` 内去重 | **不做跨用户 hash 去重**：否则可被用来探测「某人是否有同一文件」 |

- 现状 `audio_sha256` 只记录不使用（`models.py:72`），改为真正参与去重，但按上表分级。

### 5.9 配额与清理

- `quota_bytes` / `used_bytes` 按 `owner_id` 统计（blob 按引用计数计入）。
- 超限：停止接收新上传（HTTP 413 + 明确文案），不静默删用户文件。
- 清理工具：按「已备份且本地也有」批量删本地 / 按「30 天未播放」建议删云端。
- 生命周期（单机磁盘版，替代对象存储降冷）：全局池水位 > 70% 时，**90 天未访问**的云端文件可从磁盘清除，但**条目与来源索引保留**，新设备走「一键重提」恢复；清除前站内通知。【开放问题 Q4】

## 7. 平台绑定（B 站 / 抖音）

### 7.1 先回答「绑定的目的」

绑定不是为了登录 App（App 账号是邮箱），而是**让服务端以用户自己的平台身份去提取**，带来三件事：

1. **成功率**：游客请求更容易撞风控（B 站 412、抖音限流），带 Cookie 成功率明显更高。
2. **内容范围**：会员/登录可见内容、以及「收藏 / 稍后再看」这类个人列表。
3. **画质**：部分高码率需要登录态。

> 不绑定也能用（游客提取），绑定是「增强项」——这个定位要写进 UI，否则用户会以为绑定是强制的。

### 7.2 状态机

```
未绑定 → 绑定中(二维码/OAuth) → 待验证 → 已生效
                                    ↓        ↓
                                 验证失败   探活失败/平台登出
                                    ↓        ↓
                                 未绑定     已失效(自动降级游客 + 推送式提醒)
                                    ↑________|
```

- `last_checked_at` 探活：每次使用前校验 + 每日定时校验（现状字段已有）。
- 失效后自动降级游客提取并提示重新绑定，不静默失败。
- 一键解绑：立即标记失效 + 服务端停止使用 + 提示「已停止使用你的 B 站登录状态」。

### 7.3 凭据保护

- 只在服务端加密存储（现状已满足），**永不下发客户端、永不进日志**（现状 `api.py:42-53` 已对抖音回调打码）。
- 加密密钥独立于数据库保管 + 支持 `key_id` 轮换。
- **只读原则**：凭据仅用于读取/下载，绝不用于发帖、改资料、点赞等写操作。
- 使用配额：每绑定账号每日提取上限（防封号），异常（大量失败/验证码/风控页）自动熔断并降级。

### 7.4 两端差异与推进顺序

| 平台 | 现状 | 设计 |
|---|---|---|
| B 站 | 扫码得 Cookie → 服务端验证 → 加密入库（`platform_accounts.py:108-117`） | 机制保留；补状态机、探活、配额、熔断。无官方 OAuth，Cookie 路线是唯一可行解，UI 需明示用途与可解绑 |
| 抖音 | OAuth，需 `client_key/secret/redirect_uri`（`config.py:38-40`），**未配置则不可用**；只存 open_id | 送审需要企业主体，周期数周 → **MVP 先只做 B 站绑定**，抖音维持游客提取；待资质到位后接 OAuth，可申请收藏列表 scope |

**【开放问题 Q3】**：抖音绑定是否一定要上？（决定是否需要提前准备企业资质与送审）

## 8. 服务器安全：回答你的三个问题

### 8.1 「隐藏服务器真实 IP」——零预算下能做到什么，做不到什么

先说物理事实：**没有域名和 CDN，源站 IP 就是服务地址**，任何用过一次 App 的人抓包都能拿到。所以目标从「绝对隐藏」降级为「**不硬编码、防扫描、可快速切换**」：

1. **APK 不硬编码 IP**：内置的只有 remote_config 的 GitHub 地址（`raw.githubusercontent` / jsDelivr / Release 附件三路兜底），服务地址从配置读 → 反编译只能拿到「配置在哪」，拿不到「服务在哪」；**换 IP 不发版**（改一个文件全体客户端跟切）。
2. **防扫描伪装**：nginx 只响应 `Host` 头匹配内部代号的请求，其余一律 444（80 端口同样）；TLS 用已部署的 **Let's Encrypt IP 证书**（免费、短效、`deploy/tx-https` 已实现每日自动续期）。效果：端口扫描器/批量蜜罐爬虫看到的是空响应；防不住定向抓包 —— 接受。
3. **端口收敛**：只开 443；SSH 改非默认端口 + 仅密钥 + fail2ban。
4. **应用层加固补位**：没有 CDN/WAF 当挡箭牌，限流、审计、老接口鉴权从「最好有」变成「必须有」（见 8.4）。
5. **一年期限配套**：写一份「重建手册」（nginx 配置、FastAPI、数据目录、证书、密钥各就各位），目标 2 小时内可在任意新机器复活服务。

诚实结论：**防扫描不防抓包**。真实保护是「IP 不出现在 APK、搜索引擎、应用市场里」+「被打/被封/机器到期时能快速换」。

### 8.2 「去掉『从服务器提取』按钮」——同意去掉按钮，不同意去掉能力

我的建议是**把选择权从用户手里收走，而不是把能力砍掉**：

| 方案 | 评价 |
|---|---|
| 完全删掉服务端提取 | ❌ 服务端提取是手机端失败的兜底（412、风控、大文件、微信内分享），砍掉等于把成功率让出去 |
| 保留现状的两个按钮 | ❌ 用户看不懂「手机/服务器」的区别，且暴露后端存在 |
| **改成「自动」+ 一个开关**（推荐） | ✅ 手机直提优先（省带宽、不暴露服务端凭据）；失败后自动用云端重试一次；设置里一个「云端加速（失败自动重试）」开关，默认开 |

- UI 上只有「提取」一个动作，进度文案区分「正在提取… / 正在用云端重试…」。
- 批量提取（多条链接）默认走云端：并发稳、不怕手机断网。
- 现状 `ExtractScreen.kt:350-357` 的独立按钮 + `AgentScreen.kt:309` 的入口都按此收敛。

### 8.3 「隐藏 IP/端口，只留测试连接」——同意，但保留的是「状态」不是「配置」

改造后的「我的 → 服务状态」卡片：

| 展示 | 不展示 |
|---|---|
| 连接状态（正常 / 异常 / 维护中）、上次同步时间、当前区域（华东）、账号用量与配额、重新检测按钮（打 `/health`，只回成功/失败） | 域名、IP、端口、协议、HTTP 开关、任何可手填的地址 |

- 开发者调试入口：连续点击版本号 7 次解锁调试面板（显示环境、实际服务地址、请求耗时），对普通用户不可见 —— 比留一个常驻输入框安全。
- 老用户的手填地址：升级后自动迁移到 remote_config 下发的默认地址，手填值丢弃（避免有人填了内网地址后永远连不上）。

### 8.4 完整加固清单（你没提但必须做）

**应用与接口**

- 老接口补鉴权或下线（见第 6 节）—— 当前最大风险。
- 全接口限流：登录/验证码/上传/下载/提取，按 `user_id` + `IP` + `device_id` 多维度；提取类按天配额。
- 上传：大小上限、`Content-Type` 白名单 + **magic bytes 校验**、文件路径由服务端生成（绝不采信客户端文件名，防穿越）、流式落盘并即时校验大小。
- FFmpeg 处理不可信输入：**参数数组而非 shell 拼接**、超时、`ulimit`/cgroup 限制 CPU 与内存、tmp 目录每次任务独立且任务结束即清理、禁止 `-i` 之后出现用户可控的协议（防 SSRF，如 `concat:http://`）。
- 文件服务：路径一律服务端生成（防穿越）、`Content-Type` 白名单 + **magic bytes 校验**、大小上限边写边校验、nginx `secure_link` 短签 10 分钟、下载同样走限流。

**主机与运维**

- SSH 仅密钥 + fail2ban；系统定期补丁；`pip-audit` 依赖漏洞扫描。
- **备份（零预算版）**：现在**没有备份脚本**（`scripts/` 只有连手机和密钥脚本）—— 必须补。方案：SQLite 每日 `sqlite3 .backup` 快照 → `age` 加密 → 推到 **GitHub 私有仓库**（DB 只含元数据，<100 MB 量级，远低于 2 GB 附件上限，免费且异地）；**blob 不做异地备份**（体积不允许，90 GB 传 GitHub 不现实），灾后恢复靠「来源索引 + 一键重提」兜底（§5.9/§10）；加密密钥（平台 Cookie 的 KEK）**单独离线保管一份**（打印/密码管理器）—— 机器没了宁可平台凭据作废让用户重绑，也不能让密钥跟着备份明文走。每季度在本机演练一次恢复。
- 密钥管理：`SECRET_KEY`、SMTP 授权码、OAuth、平台 Cookie 加密 KEK 全走环境变量/独立密钥文件（不进仓库、不进备份明文），定期轮换。
- 审计日志（登录、绑定、注销、删除、配额变更，保留 6 个月）+ 告警（5xx 突增、异常登录、磁盘水位、提取成功率跌、SMTP 配额耗尽）。

**架构**

- **SQLite 保留**（零预算不引 Postgres）：开 WAL + `busy_timeout`，单机几百用户量级的写并发完全够用；把一次性 `schema_migrations.py` 升级为**带版本号的迁移框架**（`schema_migrations` 表 + 顺序脚本），满足单机演进，不引 Alembic 也可；Postgres 留作「换机时顺手可做」的可选项，不在本期内。
- 迁移窗口：先把现有 `owner_scope=legacy` 的数据认领到一个迁移账号（见第 12 节）。

## 10. 成本与容量（零预算、单机、一年）

假设：音频均价 4 MB（≈3–4 分钟 m4a），视频均价 30 MB（≈3 分钟 1080p）。
资源盘点：唯一一台机器 **4C / 7.5 GB 内存 / 118 GB 盘（当前余 ~28 GB，清理旧构建与日志后目标划出 80–100 GB 作全局 blob 池）**。

| 项 | 数量级 | 说明 |
|---|---|---|
| 现金支出 | **0 元** | 机器已有（一年内）、LE IP 证书免费、SMTP 免费额度、GitHub（配置分发+备份+探活）免费 |
| 元数据 DB | < 100 MB | SQLite WAL 毫无压力 |
| 音频 blob 池 | 90 GB ÷ 人均 0.4 GB ≈ **200–250 个典型用户** | 人均 100 条 × 4 MB |
| 视频 blob 池 | 90 GB ÷ 人均 3 GB ≈ **30 个全量视频用户** | **视频是音频的 ~8 倍**，单机容不下多少 |
| 换机下行流量 | 与池大小同数量级 | 腾讯轻量一般有月流量包，超了限速而非停机；换机重下本身是低频事件 |

**结论与策略**：

1. **单机容量是硬上限，不是钱的问题**：全局池水位到 85% 即停止新上传（HTTP 413 + 公告），只保留秒传与元数据同步 —— 宁可限流不可写爆盘。
2. 【决策】**音频与视频分档**：
   - GetAudio：免费额度 **2 GB/人**（约 500 条音频），默认自动备份**仅元数据**，文件按需手动/Q5 决策。
   - GetVideo：默认**不上传文件**，仅同步元数据 + 来源索引；「单条备份」手动点按，额度 1 GB —— 单机放不下几十个全量视频用户，索性不让用户形成「视频全量在云端」的预期。
3. **来源索引兜底（B 方案，成本为零）**：所有条目永久记录 `source_url + platform/video_id` 元数据，文件不在云端也能在新设备「一键重新提取」—— 这是单机小盘上唯一可持续的「跨设备拿到文件」方案。
4. **无付费档**：超限只能清理或等待（不做支付，也就没有支付合规）。
5. **一年到期的 EOL**：提前 60 天在 App 内公告 + 提供**全量导出**（元数据 JSON + 文件 zip 打包下载）；到期即关停。blob 不做异地备份（见 8.4），但元数据已在 GitHub 私库有加密副本 —— 服务会停，数据不丢。

## 12. 迁移与兼容

1. **数据认领**：现有 `owner_scope=legacy` 的条目（服务端 `data/audio` 下）提供一次性认领入口：用手机号登录后点「认领本机历史数据」，按 `device_id` + 时间窗匹配，超限需人工。
2. **游标重置**：客户端 `updatedSeq` 语义混杂（旧版为毫秒时间戳），升级后**丢弃旧游标，全量重拉一次**，并提示用户。
3. **API 版本化**：`/v2/*` 继续演进；老版本客户端（<0.9.x）到 EOL 后强制升级（remote_config 下发 `min_version`）。
4. **双写窗口**：新同步上线后保留 1 个版本只读兼容，确认无回归再下线旧 `/sync`。
5. **数据库迁移**：把 `schema_migrations.py` 升级为**版本化迁移框架**（版本表 + 顺序脚本），首版 = 现状 schema 快照，后续全部走脚本；不引 Alembic（见 8.4）。
